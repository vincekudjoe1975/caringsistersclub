## Verdict
**Stripe is NOT live. Real cards would NOT be charged right now — the app is operating in Stripe TEST mode.**

## Evidence (production)
1. **STRIPE_SECRET_KEY** — set (non-empty). Value not readable by tooling, but the operative key is a **test** key: every Stripe Checkout Session ever stored is a `cs_test_…` id (see #6). A `cs_test_` session can only be produced by an `sk_test_`/`rk_test_` key. Combined with provider = `stripe_sandbox` (unclaimed sandbox → platform injects test keys), the key is **sk_test_**, not sk_live_. *(Inferred — secret values are never returned; not a byte-read of the prefix.)*
2. **STRIPE_MODE = "live"** (confirmed via list_secrets matches_expected: true for "live", false for "test"). **IMPORTANT: this is misleading.** `grep` of `backend/server.py` shows `STRIPE_MODE` is **never referenced** anywhere in the code. Charging behavior is governed solely by `stripe.api_key = os.environ.get("STRIPE_SECRET_KEY")` (server.py:642). So STRIPE_MODE="live" does NOT make the app charge real cards.
3. **STRIPE_PUBLISHABLE_KEY** — set (non-empty). Value not readable; inferred **pk_test_** by the same reasoning (unclaimed sandbox). The donation flow uses Stripe-hosted Checkout redirect, so the publishable key isn't surfaced on a backend endpoint to confirm the prefix directly.
4. **STRIPE_WEBHOOK_SECRET** — set (non-empty). Used in `stripe.Webhook.construct_event(payload, sig, STRIPE_WEBHOOK_SECRET)` (server.py:864).
5. **Logs (last 24h, active run):** webhook endpoint is `POST /api/stripe/webhook` (not `/api/webhook/stripe`) — returning **200 OK** repeatedly, **no signature-verification failures**. Checkout endpoint is `POST /api/donations/checkout`. The only Stripe "errors" are benign `resource_missing` 404s: `No such subscription: 'sub_1UMj5ALiEefNWkHq6yFr5xgi'` (library INFO level) — a lookup for a subscription that doesn't exist, **not** an auth/signature/checkout failure.
6. **Recent checkout sessions livemode:** NO. All sessions in `payment_transactions` and `member_checkouts` are `cs_test_…` (livemode=false). Count of `cs_live_` sessions in `payment_transactions` = **0**. No payment records created after the Nov-5 secret-change redeploys (count=0 after 2026-11-05), `ticket_orders` empty — so there is no post-change session to observe, but zero live sessions have ever been created.

## Answers to the 6 questions
1. STRIPE_SECRET_KEY → **sk_test_** (test). Not sk_live_/rk_live_. *(Inferred from cs_test_ sessions + unclaimed sandbox; value itself not readable.)*
2. STRIPE_MODE → **"live"** — but it is **unused by the code** and does not control mode. Red herring.
3. STRIPE_PUBLISHABLE_KEY → **pk_test_** (inferred).
4. STRIPE_WEBHOOK_SECRET → **set** (non-empty).
5. No Stripe errors on checkout/webhook. Webhooks 200 OK, no signature failures. Only benign `resource_missing` 404 on a subscription lookup.
6. No — recent/all sessions are test-mode (`cs_test_`), zero livemode sessions.

## What must happen to go live
1. **Claim the Emergent Stripe sandbox** in the Deployment Panel → **Payments** tab and connect the organization's real (live) Stripe account. While the provider stays `stripe_sandbox` (unclaimed), the platform keeps injecting test keys regardless of STRIPE_MODE.
2. **Redeploy** after claiming, so write_secrets pulls the new `sk_live_` / `pk_live_` keys and the live webhook secret into production.
3. **Verify after redeploy:** make one real low-value donation and confirm a `cs_live_…` session id appears in `payment_transactions` and the webhook still returns 200. Until a `cs_live_` session is observed, treat it as still-test.

Note: STRIPE_MODE="live" currently gives a false impression of readiness — it has no effect in this codebase.
