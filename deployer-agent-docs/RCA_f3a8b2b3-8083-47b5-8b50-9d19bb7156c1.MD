# Production RCA — caring-sisters-clone (run f3a8b2b3-8083-47b5-8b50-9d19bb7156c1)

Deployment: `caring-sisters-clone` · live URL `https://caring-sisters-clone.emergent.host` · template farm (fastapi_react_mongo_shadcn) · prod DB `caring-sisters-clone-test_database`. All findings are from the **production** Atlas DB and the **active run's** pod logs.

---

## ISSUE 1 — Email verification link always fails ("invalid or expired")

### Root cause (confirmed)
The verification link in the email points at the **preview domain**, not production. The preview backend uses a **separate database** that does not contain the token inserted by the production signup, so the verify POST there returns 400. Production never even receives the click.

### Evidence
**(b) PUBLIC_APP_URL resolution is the bug.** The code resolves the link base as `db.settings{key:'site'}.site_url` → env `PUBLIC_APP_URL` → hardcoded preview fallback. In prod:
- The `settings{key:'site'}` document has **no `site_url` field**. It stores the correct prod URL under a *different* field name: `detected_site_url = "https://caring-sisters-clone.emergent.host"`. The code reads `.site_url` → `None`.
- There is **no `PUBLIC_APP_URL` secret** in the production run (verified via list_secrets — key absent entirely).
- Both fallbacks miss → the code falls through to the hardcoded `https://caring-sisters-clone.preview.emergentagent.com`.
- Net: every email link points to the preview domain. The correct prod URL is sitting right there in the DB, just under the wrong key name.

**(a) auth_tokens (kind 'verify').** Exactly 1 doc: `user_id=user_e857c30c3a88`, `used=false`, no `used_at`, `created_at=2026-10-12T23:12:27Z`, `expires_at=2026-10-13T23:12:27Z` (valid 24h, not expired). The token was **never consumed** — rules out an email-scanner/link-prefetch pre-consuming it. It is simply never presented to the prod backend.

**(c) Backend logs (last 24h).** `POST /api/auth/signup` → exactly **1** call, 200 OK, from 104.22.101.22 (Cloudflare edge). `POST /api/auth/verify-email` → **0 calls**. `POST /api/auth/resend-verification` → **0**. The signup at 23:12 matches the token's `created_at`. Zero verify-email hits in prod is the smoking gun: if the link pointed at prod we would see at least a logged 400. The request is landing on the preview deployment instead.

**(d) Password reset.** `POST /api/auth/reset-password` → **0 calls** in prod logs. No reset was attempted against production — same root cause (any emailed reset link would also carry the preview domain). Cannot confirm a reset "worked" because none reached prod.

### Fix (Code — E1 applies in source)
Make the prod link base resolve to the production domain. Any one of these closes it; do the first two:
1. In the PUBLIC_APP_URL resolver, read the field that actually exists: `settings['detected_site_url']` (prefer it, or write `site_url` into that doc). This alone fixes it since the correct prod URL is already stored there.
2. Replace the hardcoded preview-domain fallback with something safe (e.g. derive from the request host / `REACT_APP_BACKEND_URL`) so a missing config can never silently ship preview links in production again.

### Alternative/complementary fix (User — secrets)
Add `PUBLIC_APP_URL=https://caring-sisters-clone.emergent.host` to the backend `.env` in preview and redeploy (new key → picked up on next deploy). This is belt-and-suspenders; the code fix above is the real remediation. (Note: a secret alone won't help until the hardcoded-fallback path is also no longer reached, but with PUBLIC_APP_URL set the env branch wins before the fallback.)

## ISSUE 2 — Push alerts don't arrive on the phone

### Root cause (confirmed for the "no phone, only computer" accounts; strongly indicated for the rest)
There are **two near-duplicate admin accounts** for the same person, and the Android phone subscription is registered under only ONE of them. Pushes are delivered per `user_id`, so testing/triggering from the account that owns no phone subscription yields "computer only, phone never arrives." Where account and subscription line up, delivery is actually **succeeding** at the server — no VAPID or server fault.

### Evidence
**push_subs (3 docs, 2 distinct user_ids):**
| user_id | account | endpoint host | type | updated_at | last_ok_at | last_fail_at |
|---|---|---|---|---|---|---|
| user_29a9fdfb7abc | vinnykudjoe@gmail.com (admin) | fcm.googleapis.com | Android phone | 2026-10-12 22:17 | **2026-10-12 23:06:48** | — |
| user_29a9fdfb7abc | vinnykudjoe@gmail.com (admin) | wns2-bn3p.notify.windows.com | Windows computer | 2026-10-12 19:48 | **2026-10-12 23:06:49** | — |
| user_99dc2fb38790 | vincekudjoe@gmail.com (admin) | wns2-bn3p.notify.windows.com | Windows computer | 2026-10-11 20:49 | — | — |

- The two admin accounts are `vinnykudjoe@gmail.com` (user_29a9fdfb7abc, created 2026-10-11) and `vincekudjoe@gmail.com` (user_99dc2fb38790, created 2026-09-24) — nearly identical name/email, almost certainly the same person with two logins.
- The **only phone (FCM) subscription belongs to user_29a9fdfb7abc (vinny)**. Account **user_99dc2fb38790 (vince) has only a desktop (WNS) sub, no phone** → this is the "neither phone shows up, only the computer" case. No `push_subs` doc exists for the pending signup account either.

**No VAPID / server-side delivery failure:**
- Backend logs (24h): **0** `Push failed (` lines and **0** `Push subscription saved` lines. No 401/403 VAPID-mismatch, no 413.
- `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` all **exist and are non-empty** in prod. I cannot read the sealed values to byte-compare the pair, BUT the empirical signal says they are a working pair: a mismatch would produce 401/403 and `last_fail_at` — instead we see `last_ok_at` set and zero failures. (The `VAPID_SUBJECT` matches_expected=false in my probe only means my guessed value was wrong; it does not indicate a problem.)
- `push_log` corroborates success: the post-deploy "Test alert — Your phone alerts are working" at 2026-10-12 23:06:49 shows `members:1, delivered:2, failed:0` — i.e. both of vinny's devices accepted the push (the two `last_ok_at` timestamps at 23:06). Earlier sends (2026-10-11) predate the new `last_ok_at/last_fail_at` fields, which is why vince's WNS sub has neither field yet — it simply hasn't been targeted by a send since the new-fields deploy, not evidence of a failure.

### Interpretation
1. **Primary:** phone subscription vs. tested-account mismatch. The phone is subscribed under vinnykudjoe; the account used on desktop (vincekudjoe) has no phone sub, so its alerts are computer-only. The admin "Registered devices" list evidently shows devices across accounts, which makes the Android device *appear* associated with the account under test even though sends are scoped by `user_id`.
2. **Secondary (only if the phone still shows nothing for the vinny account despite delivered=success):** the push service (FCM) returned 201 and the server recorded `last_ok_at`, so anything beyond that is client-side — the browser/OS did not display it (service-worker not showing the notification, notification permission revoked, battery/Doze suppression, or an expired endpoint). This is not a server or VAPID defect.

### Fixes
- **User (user_checks_and_decides):** Decide which admin account is canonical and consolidate the duplicates (`vinnykudjoe@gmail.com` user_29a9fdfb7abc vs `vincekudjoe@gmail.com` user_99dc2fb38790). Then subscribe the Android phone from within that single canonical account so its `push_subs` doc carries the FCM endpoint under the `user_id` you actually test with.
- **User (test_and_verify):** For the account that *does* own the FCM sub (vinny), trigger a real send and confirm on the phone whether the notification is displayed. Server shows delivered/201; if nothing appears, check the phone's site notification permission and that the PWA/service worker is still installed — the issue is client/OS-side, not the backend.
- **Code (optional, E1):** Make the admin "Registered devices" list disambiguate which `user_id`/account each device belongs to, so a device registered under a different account isn't read as the current account's. This is an inferred UI improvement from the symptom, not a confirmed code defect.
