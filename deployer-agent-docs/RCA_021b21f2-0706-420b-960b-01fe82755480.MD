# RCA — Caring Sisters Club: login/logout failing on www + iOS PWA + the join flow

Deployment: caring-sisters-clone (run 021b21f2-0706-420b-960b-01fe82755480, active/healthy)
Frontend type: **Cloudflare** (static from R2 + worker that proxies `/api` to the k8s backend on each hostname)
Hosts in play: apex `https://caringsistersclub.org`, `https://www.caringsistersclub.org`, default `https://caring-sisters-clone.emergent.host`

## Symptom
Login/logout unreliable in production, specifically for (a) new members going through Join → /members sign-up → confirm email → application, and (b) iPhone Home-Screen (iOS PWA/Safari) users. Apex users are mostly fine.

## What the evidence shows
1. **Frontend calls the API on an absolute host, not the page's own origin.**
   `frontend/src/lib/api.js`: `axios.create({ baseURL: `${REACT_APP_BACKEND_URL}/api`, withCredentials:true, headers:{'X-Requested-With':'XMLHttpRequest'} })`.
   `REACT_APP_BACKEND_URL` is confirmed (list_secrets matches_expected=true) to be **`https://caringsistersclub.org`** (the apex).
   => Any page NOT loaded on the apex (www, the emergent.host default, and PWA installs that opened on those hosts) makes **cross-origin** XHR to the apex.

2. **Backend logs (24h) confirm the cross-origin break:**
   - Every `OPTIONS /api/auth/{me,session,login,signup}` returns **400 Bad Request**. This is Starlette `CORSMiddleware` returning *"Disallowed CORS origin"* — i.e. the preflight's `Origin` (the www / emergent.host page) is not in `CORS_ORIGINS`.
   - Repeated pattern: `POST /api/auth/session → 200` immediately followed by `GET /api/auth/me → 401` from the same Cloudflare edge IP. The session cookie was set on the apex response but not returned on the follow-up request.
   - 125 of 190 auth requests are `401 Unauthorized` — sessions are not persisting.
   - `CORS_ORIGINS` does NOT equal `https://caringsistersclub.org,https://www.caringsistersclub.org` (list_secrets matches_expected=false), so www/emergent-host origins are not allowed.

3. **Cookie is a third-party cookie off the apex.**
   `response.set_cookie("session_token", httponly=True, secure=True, samesite="none", path="/")` — SameSite=None; Secure; **no Domain** (lines 214-216, 341). Host-only on the apex. On a www/emergent.host page this is a cross-site cookie → **Safari/iOS ITP blocks storing & sending it** → login never persists. This is exactly the `session 200 → me 401` log pattern, and why iPhone Home-Screen installs fail hardest.

4. **Verification emails point members at the wrong host (the join-flow break).**
   DB `settings.site`: `site_url = "https://caring-sisters-clone.emergent.host"` (admin-set), `detected_site_url = "https://caringsistersclub.org"`.
   `_refresh_site_url()` prioritizes the admin `site_url`, so `PUBLIC_APP_URL = https://caring-sisters-clone.emergent.host`, and `_send_verify` builds the confirm link as `…emergent.host/verify-email?token=…` (line 351).
   => A new member who signs up on the apex is emailed a link to the **emergent.host** host, confirms there, and then logs in there — which is cross-origin to the apex API → cookie blocked (see #3). The Join flow therefore fails on Safari/iOS.

5. **www→apex redirect does not rescue the failing cases.**
   list_domains: both `caringsistersclub.org` and `www.caringsistersclub.org` are verified, SSL active, `root_redirect_enabled=true`. check_domain_status: both DNS-linked. But an installed iOS PWA keeps its install-host start_url (manifest `start_url:/members`, `scope:/` are relative) and a server 301 won't move an already-open standalone app, and the emergent.host default host is not redirected to the apex. So www/PWA/emergent-host users keep operating on a non-apex origin. (Partly inferred — my tools can only probe the emergent.host default URL, not the custom hostnames, so I could not exercise the live www→apex 301 directly.)

6. **CSRF and logout.** The axios client sends `X-Requested-With: XMLHttpRequest`, so the CSRF middleware is satisfied — CSRF is NOT the cause. Logout fails on non-apex hosts for the same reason as login: its `OPTIONS` preflight 400s (cross-origin) and/or the cookie was never stored. Minor secondary issue: `response.delete_cookie("session_token", path="/")` (line 241) omits `secure`/`samesite`, so the delete may not match the original `SameSite=None;Secure` cookie in some Safari versions and the cookie can linger.

## Root cause
The frontend is hard-wired to call the API at the absolute apex host (`REACT_APP_BACKEND_URL=https://caringsistersclub.org`) even though the Cloudflare worker already proxies `/api` on whatever hostname serves the page. Every non-apex host (www, emergent.host default, and iOS Home-Screen PWAs installed from those) therefore issues cross-origin, credentialed requests to the apex. Those requests (a) fail CORS preflight (`OPTIONS → 400`, origin not in `CORS_ORIGINS`) and (b) carry a `SameSite=None` host-only cookie that Safari/iOS ITP treats as third-party and blocks — so sessions don't persist. Compounding it, `settings.site.site_url` is set to the emergent.host default, so verification emails route new members to the wrong (cross-origin) host.

## Fixes (in priority order)
### Fix 1 — Code (E1): call the API same-origin instead of the absolute apex  ← root fix
In `frontend/src/lib/api.js`, make the axios baseURL **relative/same-origin** (`/api`, or `window.location.origin + '/api'`) instead of `${REACT_APP_BACKEND_URL}/api`. Because the Cloudflare worker proxies `/api` on every hostname that serves the app, this makes apex, www, emergent.host and the iOS PWA all **first-party** — eliminating the CORS preflight 400s and the third-party-cookie/ITP breakage in one change. Audit the other `${REACT_APP_BACKEND_URL}${path}` image/download usages similarly (relative is fine same-origin).
(Note: `REACT_APP_BACKEND_URL` is a platform/system-managed key, so hand-editing the baked value is not the right lever — using a relative `/api` is.)
Also pass `secure=True, samesite="none", path="/"` to `response.delete_cookie` in the logout handler so logout reliably clears the cookie in Safari.
Diagnosed from source in a sandbox; NOT runtime-verified — the live Safari/ITP cookie block cannot be reproduced without a real browser + production secrets.

### Fix 2 — User (admin settings / DB): correct site_url so emails use the apex
Set the app's Website address (`settings.site.site_url`) to `https://caringsistersclub.org` (or clear it so the detected apex / canonical is used). Then verification + password-reset emails link to the apex and new members confirm & log in on the same origin as the API. The admin can do this by signing in on the apex (`https://caringsistersclub.org`, NOT www/emergent.host — same-origin login works there) and editing Website address, or by updating the `settings` document (`key:"site"`) directly.

### Fix 3 — User (interim, until Fix 1 ships): keep everyone on the apex
- Direct members to `https://caringsistersclub.org` (not www, not the emergent.host URL). Ensure `www → apex` is a hard 301 at the edge and treat the apex as canonical.
- iPhone users who installed from www/emergent.host should delete the Home-Screen app and reinstall it from the apex so the PWA runs first-party.
- Optional/partial: add `https://www.caringsistersclub.org` and `https://caring-sisters-clone.emergent.host` to the `CORS_ORIGINS` secret so cross-origin preflights stop returning 400. This helps desktop Chrome but will NOT fix Safari/iOS — ITP still blocks the third-party cookie — so it is not a substitute for Fix 1.
